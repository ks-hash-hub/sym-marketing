URL Structure — How the Link Works
Each release gets a permanent, unique URL based on its UPC (or Airtable Record ID). Airtable can generate this automatically using a formula — no manual link creation needed. When someone opens the URL, the app reads the ID and loads the correct artist profile.

Airtable formula: "https://labs.symphonic.com/" & {UPC}
Note on the domain: Cloud Run provides an auto-generated URL immediately on deploy. The clean labs.symphonic.com address requires a DNS record pointed at the Cloud Run service — a one-time change by whoever manages Symphonic's domain.

Build Plan

Three phases.
Ship early, improve often.

The goal is to get something real in people's hands quickly, then layer in live data and a proper backend as the tool proves itself.

Phase 1 — MVP Get a shareable link working
🔗
To Build
URL Routing by UPC / Record ID
Each release needs its own permanent URL. When someone opens that URL, the app loads the correct artist profile automatically.
How we make it happen
Add React Router to the existing app. Read the ID from the URL, match it to a release in the data, load that profile. Airtable generates the link automatically via a formula column — no manual work for the team.
☁️
To Build
Hosted on Google Cloud Run
The tool lives at a real URL on Google Cloud Run — containerized, scalable, and consistent with how other Symphonic internal tools will be deployed. Anyone on the team opens a link in their browser, no setup required.
How we make it happen
Package the React/Vite app in a lightweight Docker container and deploy to Google Cloud Run using Symphonic's existing Google Cloud account. Connects to GitHub Enterprise for CI/CD — every push to main auto-deploys. Default Cloud Run URL works immediately; custom domain (labs.symphonic.com) added via a DNS record pointed at the service once ready.
🔐
Built-in with Cloud Run
Google Authentication Gate
Because this is an internal tool, access should be restricted to Symphonic team members only. Google Cloud Run supports this natively — anyone without a Symphonic Google account is blocked before the page even loads. No login screen to build, no passwords to manage.
✓ Only @symdistro.com Google accounts can access the app
✓ No auth code to write — configured at the infrastructure level
✓ Same auth model as every other Symphonic internal tool — consistent experience
✓ Access to Google Vertex AI for future features (driver enrichment, audio analysis)
How we make it happen
Cloud Run's Identity-Aware Proxy (IAP) handles authentication. Enable it on the service, configure it to require a Symphonic Google account, done. Works across all future Symphonic labs apps — this is the standard deployment pattern the team is building toward.
📋
Already Built
Airtable Live Data Connection
Release schedule, driver submissions, and pickup history are already pulling from live Airtable data when an API token is present.
What's in place
The app reads from three Airtable tables via the REST API: Release Schedule, Driver Submissions, and Pickups. Falls back to demo data automatically if no token is set.
🎯
Foundation Built
Core Profile Page
The profile page structure exists and runs locally on demo data — but the layout, displayed signals, and score formula all need to be finalized with the team before this is considered done.
What still needs to happen in Phase 1
Two open decisions: (1) What we show — finalize which signals and sections appear on the profile page with input from the marketing team. (2) How the score is calculated — the SYM Score pillars and weights need to be agreed on collaboratively (this is the "scorecard we build together" from the brief). Once both are locked, the profile page becomes the canonical view that the shareable link resolves to.
🧮
To Define
SYM Score Formula
The scoring model has a proposed structure (5 pillars: Pickups, Audience, Social, Drive, Consistency) but the weights and thresholds need to be validated and agreed on with the marketing team before they're locked in.
How we finalize it
Run the proposed formula against a sample of real releases, review the outputs with reps, and adjust weights until the scores feel right. The formula lives in the app code — once agreed, it becomes the single source of truth that feeds both the profile page and the nightly Airtable score write-back.
Phase 2 — Live Data Replace demo data with real API data
📊
Needs API Key
Chartmetric Integration
Historical playlist adds and drops, social follower counts, similar artist placements, organic editorial placements — all currently showing as demo data.
How we make it happen
Symphonic already has a Chartmetric API key (stored in 1Password). Wire the existing API layer to real Chartmetric endpoints for playlist history and social stats. Note: Chartmetric is a paid API — calls should be cached to avoid unnecessary spend.
🎵
Free Tier
Spotify API Integration
Related/similar artists (seeds the Playlist Targets feature), audio features (energy, mood, tempo), and current playlist placements.
How we make it happen
Register a Spotify app (free), use client credentials auth flow. No user login required. Pull related artists by artist ID and use those to query Chartmetric for their playlist history.
🔄
To Build
Scheduled Score Sync — Write Back to Airtable
Once scores are calculated, they get written back into the Airtable release schedule as regular number fields. This means the team can sort, filter, and group releases by score directly inside Airtable — no need to open the app just to find weak releases or rank a priority stack.

↕ Sort all releases by SYM Score descending
⊟ Filter for Score < 40 — find weak releases early

⚠ Filter "Has Driver Submission = No" to find gaps

📊 Build dashboards on top of score data
How we make it happen
A scheduled job runs nightly — calculates scores for all active releases using the same logic as the profile page, then writes each pillar score back to Airtable via the REST API. Airtable fields are plain Number type so they sort and filter natively. A "Last Score Update" date field shows when the data was last refreshed. The score logic stays in one place (the app) — Airtable just stores the output.
🔑
Security Note
API Key Handling
The current setup uses environment variables that are bundled into the front end — fine for internal use and Airtable (low risk), but needs to move server-side before Chartmetric goes live at scale.
How we make it happen
For Phase 2, paid API calls (Chartmetric, Songstats) get routed through a lightweight server-side function running on Cloud Run so the key is never exposed in the browser. Since the app is already containerized on Cloud Run, adding a small API proxy is just adding a route to the same service — no extra infrastructure. Free APIs (Spotify public endpoints) can stay client-side.
Phase 3 — Backend Scale it, share it, build on it
🗄️
Future
Data Caching Layer
Instead of hitting Chartmetric on every page load, store API responses in a database. Profiles refresh on a schedule, not on demand — keeps costs predictable and pages fast.
How we make it happen
Supabase (Postgres) is the cleanest fit — stores cached API responses, artist records, and score history. Syncs with Airtable on a schedule. Other Symphonic tools can read from the same database without re-pulling from external APIs.
🔌
Future
Airtable Extension — Popup with Radar & Profile
The extension lives in Airtable's sidebar. Select any release row and it renders a popup with the radar strength graph, score breakdown, top playlist targets, and a driver warning flag — all without leaving Airtable. A "View Full Profile" button at the bottom opens the full standalone page at that record's URL.
What the popup shows
◎ Radar chart — 6-axis strength profile
◎ SYM Score + pillar breakdown bars
◎ Top 3–5 playlist targets with match count
◎ Driver submission warning if nothing on file
◎ View Full Profile → opens labs.symphonic.com/[record-id]
How we make it happen — step by step
Airtable has a first-party feature called Extensions (formerly Apps). It lets you build a small React app that runs inside a panel in Airtable's sidebar — no iframes, no separate login. Here's exactly how we build it:
1
Install the Airtable Blocks SDK
Airtable provides an official SDK (@airtable/blocks) that gives the extension access to the current base, selected records, and all field values. We scaffold a new extension project using their CLI — it's a standard React/Node setup.
2
Read the selected record
When a rep clicks a row in the Release Schedule, the SDK fires a cursor event. The extension reads cursor.selectedRecordId, then pulls the UPC and SYM Score fields directly from that record — no API call needed since those values are already in Airtable from the nightly sync.
3
Fetch additional data for the popup
The radar chart and playlist targets aren't stored in Airtable — they come from our backend. The extension makes one authenticated call to api.labs.symphonic.com/profile/[upc] and gets back the full profile data as JSON.
4
Render the popup UI
The extension renders the radar chart, score breakdown, and top playlist targets as React components inside the Airtable sidebar panel. It uses Airtable's built-in UI components for things like loading states, so it looks native to the Airtable environment.
5
Install it into the base
Once built, we upload the extension to Airtable's marketplace (private/internal listing — not public). Any team member opens the Release Schedule base, clicks Extensions in the toolbar, and installs it once. After that it's permanently available in their sidebar on any device. Requires Airtable Pro plan or higher.

Order of Operations

What we build,
in what order.

Sequenced to get a shareable link in front of the team as fast as possible, then layer in real data from there. (subject to change)

1 Add URL routing by UPC / Record ID Makes every artist profile reachable by a permanent link. Required before anything can be shared. Phase 1

6 Wire Chartmetric API for live social & playlist data Now that the proxy is in place and the Spotify pipeline is validated, connect Chartmetric safely through the server-side layer. Replaces all demo data with real placement history, social stats, and playlist targets. Phase 2
7 Set up nightly score sync → write back to Airtable Scores, pillar breakdowns, driver flag, and playlist target count land in Airtable every night. The team can sort, filter, and build automations on top of them without ever opening the app. Phase 2
9 Add caching layer (Supabase) Store API responses so pages load instantly and paid API calls aren't triggered on every visit. Phase 3
10 Build Airtable Extension — radar popup + "View Full Profile" button Sidebar extension renders the radar graph, score breakdown, top playlist targets, and driver warning for whichever row is selected. Score bars read directly from the Airtable fields (already there from nightly sync). "View Full Profile" opens labs.symphonic.com/[record-id] in a new tab. Phase 3
11 Map labs.symphonic.com to Cloud Run service Add a DNS record pointing labs.symphonic.com at the Cloud Run service. One change — all existing links automatically work at the clean URL. Requires access to Symphonic's DNS settings. Phase 3
